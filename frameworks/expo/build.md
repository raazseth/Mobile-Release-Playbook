# Expo Build

Expo provides a managed build workflow through **EAS Build**. It can create Android and iOS binaries in consistent cloud build environments, manage or use signing credentials, and integrate with CI/CD and EAS Workflows.

This guide focuses on **building a release artifact safely**.

It does not replace the shared documentation for:

- project configuration
- environments
- versioning
- signing
- testing
- store submission

Use those guides for the broader release process.

The build flow is:

```text
Source
 ↓
Configuration
 ↓
Environment
 ↓
Build profile
 ↓
EAS Build
 ↓
Artifact
 ↓
Inspect
 ↓
Test
 ↓
Submit
```

The key rule is:

> **A successful EAS build only proves that a binary was produced. It does not prove that the binary is ready for production.**

---

# 1. What EAS Build does

EAS Build takes the project source and produces a native application binary.

Typical outputs are:

```text
Android
→ .aab for store distribution
→ .apk for certain internal/device workflows

iOS
→ .ipa for distribution
```

EAS Build can also handle native signing credentials through EAS or use credentials supplied by the project.

The build system is responsible for producing the artifact.

Your release process is responsible for proving that the artifact is correct.

---

# 2. Build profiles

EAS Build uses **build profiles** in:

```text
eas.json
```

A build profile is a named set of build configuration.

A common project has:

```text
development
preview
production
```

These names are conventions, not requirements. Custom profile names are supported. If `--profile` is omitted, EAS CLI uses the `production` profile when one exists.

A simple setup:

```json
{
 "build": {
 "development": {
 "developmentClient": true,
 "distribution": "internal"
 },
 "preview": {
 "distribution": "internal"
 },
 "production": {}
 }
}
```

This is the standard starting point generated by EAS tooling.

---

# 3. Development, preview, and production builds

Use each profile for a different job.

## Development

Used for active development.

Typical configuration:

```text
developmentClient: true
distribution: internal
```

Development builds include developer tooling and are not intended for app-store submission.

Use them for:

- native development
- debugging
- developer testing
- testing native dependencies
- sharing a development binary with the team

---

## Preview

Used for shared release validation.

Typical configuration:

```text
distribution: internal
```

Use it for:

- QA
- internal testers
- release candidates
- realistic production-like validation
- device testing before store submission

Preview is especially useful when the team needs a stable installable binary without submitting it to the stores.

---

## Production

Used for store-distributed builds.

Typical configuration:

```json
{
 "build": {
 "production": {}
 }
}
```

Production builds are intended for App Store / Google Play distribution or store-facilitated testing such as TestFlight. Expo documents store builds as the production build type.

Do not treat a production profile as proof that the app is production-ready.

---

# 4. Build the project for EAS

If EAS Build has not been configured:

```bash
eas build:configure
```

This creates or updates:

```text
eas.json
```

and configures the project for EAS Build.

Before running it:

```text
Check Git status
Check Expo configuration
Check identifiers
Check environment model
Check versioning
```

Do not blindly commit every generated change.

Review the diff first.

---

# 5. Install and use EAS CLI

EAS commands require EAS CLI. Expo documents the current installation and CLI workflow in its EAS documentation.

Typical usage is:

```bash
eas --version
```

Then:

```bash
eas build:configure
```

and:

```bash
eas build --platform android
```

or:

```bash
eas build --platform ios
```

or:

```bash
eas build --platform all
```

The current Expo documentation confirms `eas build --platform all` as the standard command for producing Android and iOS binaries together.

Always verify the installed EAS CLI and project Expo SDK when a command behaves differently from this guide.

---

# 6. Build a specific profile

Use:

```bash
eas build --profile preview --platform android
```

or:

```bash
eas build --profile production --platform android
```

For iOS:

```bash
eas build --profile preview --platform ios
```

```bash
eas build --profile production --platform ios
```

For both:

```bash
eas build --profile production --platform all
```

The profile determines the build configuration.

The platform determines which native application is produced.

---

# 7. Do not rely on the default profile accidentally

This works:

```bash
eas build --platform ios
```

when the intended profile is `production` and `production` exists.

But for release automation, explicit is better:

```bash
eas build \
 --profile production \
 --platform ios
```

or:

```bash
eas build \
 --profile production \
 --platform all
```

This makes the release intent visible in:

```text
terminal history
CI logs
scripts
pull requests
release documentation
```

The EAS CLI currently defaults to the `production` profile when no profile is specified and a `production` profile exists.

Do not rely on that default for critical automation.

---

# 8. Build profile and environment

A build profile should map clearly to the intended environment.

Example:

```json
{
 "build": {
 "development": {
 "environment": "development"
 },
 "preview": {
 "environment": "preview"
 },
 "production": {
 "environment": "production"
 }
 }
}
```

EAS supports the `environment` property for selecting the EAS environment used during the build.

This should align with:

```text
Build profile
 ↓
Environment
 ↓
API
 ↓
Authentication
 ↓
Analytics
 ↓
Push
 ↓
Other services
```

Do not let:

```text
production profile
```

silently resolve:

```text
staging environment
```

unless that is an intentional, documented workflow.

---

# 9. Build profile and environment are different

Do not confuse:

```text
Profile
```

with:

```text
Environment
```

A profile describes how to build.

An environment describes which configuration/services the app uses.

For example:

```text
Profile:
production

Environment:
production
```

is common.

But:

```text
Profile:
production-sandbox

Environment:
preview
```

can also be valid if the project intentionally needs it.

Keep the relationship explicit.

---

# 10. Environment variables

EAS supports environment variables through:

```text
EAS environments
eas.json profile env
EAS Workflows
```

The `env` property in an `eas.json` build profile can set values used during the build, including when evaluating `app.config.js` locally and on the EAS builder. Expo specifically notes that values in this `env` field should be values safe to commit, not passwords or secrets.

Example:

```json
{
 "build": {
 "preview": {
 "environment": "preview"
 },
 "production": {
 "environment": "production"
 }
 }
}
```

Prefer EAS environment variables for environment-managed values when using EAS.

Do not put secrets directly into `eas.json`.

---

# 11. Secret handling

Never put production secrets into:

```text
eas.json
app.config.ts
app.json
EXPO_PUBLIC_*
source code
Git history
```

Use protected secret storage.

The distinction is:

```text
Build configuration
→ public/non-sensitive values

Secret storage
→ sensitive credentials
```

Remember:

> **If a secret is bundled into the mobile application, it is no longer secret.**

See:

```text
foundations/release-environments.md
signing/security/
```

for the broader rules.

# 12. Validate configuration before building

Before starting an expensive cloud build:

```bash
npx expo-doctor
```

and, where appropriate:

```bash
npx expo install --check
```

The repository's shared configuration guidance recommends these as useful Expo configuration checks, while making clear that they do not prove the application works.

Then inspect the resolved Expo configuration:

```bash
npx expo config
```

For public runtime configuration:

```bash
npx expo config --type public
```

The resolved configuration matters more than the source file alone.

# 14. Build the preview artifact first

For a new release, prefer:

```text
Development
 ↓
Preview
 ↓
Production
```

rather than immediately building production.

Example:

```bash
eas build \
 --profile preview \
 --platform all
```

Then:

```text
Install
→ test
→ fix
→ rebuild
```

Only after the preview artifact is acceptable:

```bash
eas build \
 --profile production \
 --platform all
```

This reduces the chance of discovering release configuration problems after producing the store artifact.

---

# 15. Internal distribution

Preview builds commonly use:

```json
{
 "distribution": "internal"
}
```

Expo documents internal distribution as a way to share installable builds directly with testers.

A useful flow is:

```text
Preview build
 ↓
EAS build URL
 ↓
Tester installs
 ↓
Real-device testing
```

Internal distribution is not the same as:

```text
TestFlight
Google Play testing
Public production
```

Use the correct testing layer for the risk you are trying to validate.

---

# 16. Android artifact choice

For store distribution, Android production builds should normally produce:

```text
.aab
```

EAS Build uses:

```text
"buildType": "app-bundle"
```

for an Android App Bundle.

This corresponds to:

```text
:app:bundleRelease
```

Expo's current EAS schema documents `app-bundle` as the default production-oriented artifact type and `apk` as an alternative when an installable APK is specifically needed.

Use APK when you have a real need such as:

- direct device installation
- certain internal workflows
- specific test infrastructure

Do not use APK for Play Store production just because it is easier to install.

---

# 17. iOS production artifact

iOS production builds are distributed through Apple's supported distribution mechanisms.

For a normal store workflow:

```text
EAS Build
 ↓
iOS archive
 ↓
IPA
 ↓
App Store Connect
 ↓
TestFlight / App Review
```

Do not treat a locally installed development build as equivalent to the production distribution artifact.

The signing and distribution context are different.

---

# 18. Signing during EAS Build

EAS can manage app signing credentials or use credentials provided by the project.

For a first production build, understand:

```text
Which credentials are being used?
Who owns them?
Where are they stored?
Which application identifier do they belong to?
How can they be recovered or rotated?
```

For production:

```text
Identifier
+
Signing
+
Store record
```

must agree.

See:

```text
signing/ios/
signing/android/
signing/security/
```

Do not store private signing credentials in Git.

---

# 19. Credentials source

EAS supports credential sources including:

```text
remote
local
```

The EAS configuration reference documents `credentialsSource` and notes that EAS-managed credentials are the default option.

Choose deliberately.

### Remote credentials

Useful when:

```text
EAS manages credentials
Team shares release infrastructure
```

### Local credentials

Useful when:

```text
Organization controls signing material
Existing credential management must be preserved
Custom signing workflow requires it
```

The correct choice depends on the project's security and operational model.

---

# 20. Do not treat credentials as build configuration

Keep these concepts separate:

```text
Build configuration
→ how the application is built

Signing credentials
→ proof that the organization is authorized to distribute it

Store credentials
→ authorization to submit/manage the store listing
```

A build can succeed while submission credentials are wrong.

A submission can be authorized while the binary is incorrectly configured.

Verify each layer independently.

---

# 21. Versioning during EAS Build

EAS can manage application build versions.

The current EAS configuration supports:

```json
{
 "build": {
 "production": {
 "autoIncrement": true
 }
 }
}
```

EAS documents `autoIncrement` as controlling automatic version/build-number increments.

For example:

```text
Android
versionCode:
42 → 43

iOS
buildNumber:
42 → 43
```

The exact behavior depends on the configured app-version source and platform.

Do not enable automatic versioning without deciding which system owns the version.

See:

```text
foundations/versioning.md
```

---

# 22. Remote version management

EAS can store app version values remotely.

The current EAS tooling supports commands such as:

```bash
eas build:version:get
```

```bash
eas build:version:set
```

```bash
eas build:version:sync
```

Expo documents these commands for reading, setting, and syncing versions managed through EAS.

If you migrate from manual version management:

```text
Find latest production build
 ↓
Record current values
 ↓
Configure EAS version source
 ↓
Set correct starting values
 ↓
Build test release
 ↓
Verify
```

Never let a migration reset production build numbers accidentally.

# 23. Build reproducibility

A production build should be traceable to:

```text
Git commit
+
lockfile
+
Node/runtime version
+
Expo SDK
+
EAS profile
+
environment
+
version
+
build number
```

The goal is:

```text
Production artifact
 ↓
exact source state
 ↓
exact configuration
```

EAS build profiles can specify runtime versions such as Node and package-manager versions, helping make the build environment explicit.

Pin only what the project actually needs.

Do not create an unnecessarily complicated build matrix.

---

# 24. Lockfile and dependency state

Before a release build:

```text
package.json
+
lockfile
```

must be consistent.

Do not build production from a dirty dependency state.

Check:

```bash
git status
```

Then inspect:

```text
package.json
lockfile
Expo SDK
native dependencies
```

If dependencies changed:

```text
Install
→ validate
→ test
→ build
```

Do not casually change dependencies during the release build process.

---

# 25. Build environment versions

A production build can depend on:

```text
Node
package manager
Expo SDK
React Native
Xcode
Android SDK
Gradle
Java
native dependencies
```

EAS provides controlled build images and allows configuration of some build tooling versions.

Do not pin every version just because you can.

Pin versions when:

- reproducibility matters
- a dependency requires a specific version
- CI drift caused real failures
- the project needs controlled upgrades

---

# 26. Build cache

EAS supports build caching.

Caching can speed up builds, but cache configuration should not become a debugging mystery.

If a build behaves strangely after dependency/configuration changes:

```text
Check the build
→ inspect cache assumptions
→ invalidate cache when justified
→ rebuild
```

Do not disable caching permanently as a first response to every build failure.

The EAS configuration supports cache configuration and cache invalidation through a cache key.

# 31. Development build vs production build

These are not interchangeable.

Development build:

```text
Developer tooling
Debugging
Internal distribution
Fast iteration
```

Production build:

```text
Release configuration
Production signing
Store distribution
Production services
```

A feature working in development does not prove it works in production.

Common release-only failures include:

- native configuration
- signing
- permissions
- environment variables
- minification
- release-mode behavior
- deep links
- push notifications
- production API configuration

```text
 ↓
Merge
 ↓

 ↓

 ↓

 ↓

 ↓
```


# 36. EAS Workflows

EAS Workflows can automate build and release jobs.

Use automation for:

```text
Validation
Build
Artifact generation
Testing
Submission preparation
```

Keep high-impact actions bounded.

A good boundary is:

```text
AI/CI
→ prepare

Human
→ approve

Automation
→ execute approved release
```

The exact workflow should match the team's release model.

Do not create an orchestration system just to replace a small build command.

---

# 37. Automatic submission

EAS supports connecting builds to submission workflows and can auto-submit successful builds when configured.

Use automatic submission only when:

```text
Build validation is strong
+
Correct artifact is selected
+
Environment is verified
+
Store metadata is ready
+
Human approval model is intentional
```

For a new project, manual approval before first production submission is usually safer.

Automation should remove repetitive work, not remove release accountability.

# 38. Build failure triage

When an EAS build fails:

```text
1. Identify build ID
2. Identify platform
3. Identify profile
4. Inspect build logs
5. Identify first meaningful error
6. Determine whether it is configuration/dependency/native/tooling
7. Reproduce locally when practical
8. Fix
9. Rebuild
```

Do not start by changing five unrelated configuration values.

Find the first real failure.

# 41. Build inspection with AI

AI can help analyze EAS build failures.

A good workflow:

```text
Build logs
 ↓
AI identifies likely failure
 ↓
AI separates evidence from hypothesis
 ↓
Developer verifies
 ↓
Minimal fix
 ↓
Rebuild
```

Prompt:

```text
Analyze this Expo EAS Build failure.

Project:
Expo / React Native

Build:
<platform>
<profile>
<build ID>

Recent change:
<change>

Return:

1. FIRST REAL ERROR
2. DIRECT CAUSE
3. EVIDENCE FROM LOG
4. LIKELY ROOT CAUSE
5. WHAT IS ONLY A HYPOTHESIS
6. MINIMAL FIX
7. HOW TO VERIFY
8. WHAT NOT TO CHANGE

Do not invent Expo or platform requirements.

Do not recommend unrelated configuration changes.

Do not modify production configuration.

If the log does not contain enough evidence, say NEEDS MORE EVIDENCE.
```

AI should not be allowed to turn a weak hypothesis into an automatic production change.

# 49. Common failure: wrong build profile

### Symptom

The build is missing production configuration or contains development tooling.

### Check

```bash
eas build --profile production --platform <platform>
```

Then inspect:

```text
eas.json
resolved config
environment
```

### Fix

Use the intended profile.

Do not fix the symptom by adding random environment variables to the application.

# 50. Common failure: wrong environment

### Symptom

Production binary points to staging.

### Check

```text
eas.json
EAS environment
app.config.ts
environment variables
resolved public configuration
```

### Fix

Correct the environment mapping and rebuild.

If the incorrect value was bundled into the binary, the existing binary is still wrong.

# 51. Common failure: Android produces APK instead of AAB

### Symptom

The production workflow creates:

```text
.apk
```

when a Play Store bundle is expected.

### Check

```text
eas.json
buildType
gradleCommand
profile inheritance
```

The EAS schema documents:

```text
app-bundle
→ .aab

apk
→ .apk
```

and recommends App Bundles for store submission.

### Fix

Use the intended production build configuration.

# 52. Common failure: build number already exists

### Symptom

The store rejects the binary because its platform build identifier conflicts with an existing build.

### Check

```text
Current store build
EAS version source
autoIncrement
manual build number
```

### Fix

Increment the platform build identifier.

If using EAS version management, inspect:

```bash
eas build:version:get
```

before changing values.

---

# 53. Common failure: production build works locally but fails on EAS

### Check

```text
Node version
Package manager
Lockfile
Environment variables
Native tooling
Config plugins
Credentials
```

Then compare:

```text
Local
vs
EAS
```

Do not assume:

```text
works locally
```

means:

```text
production build is reproducible
```

The purpose of EAS is partly to provide a consistent cloud build environment, so differences between local and cloud builds should be investigated rather than ignored.

# 54. Common failure: build succeeds but app is wrong

This is one of the most dangerous failures.

Example:

```text
Build:
SUCCESS

App:
staging API
```

The build system did exactly what it was configured to do.

The problem is configuration.

Check:

```text
resolved config
environment
API URL
identifiers
runtime config
native config
```

This is why:

> **Build success is not release success.**

# 55. Common failure: native project drift

### Symptom

Expo configuration says one thing, native project says another.

Example:

```text
Expo:
com.example.app

iOS:
com.example.oldapp
```

### Check

```text
app.config.ts
ios/
android/
Prebuild workflow
config plugins
```

### Fix

Identify the actual source of truth and bring the project into alignment.

Do not blindly overwrite native changes.

---

# 56. Common failure: stale cache

### Symptom

A build appears to use old dependencies or configuration.

### Response

First inspect the build inputs.

Then, if cache is actually suspected:

```text
Invalidate the relevant cache
 ↓
Rebuild
 ↓
Compare
```

Do not make cache deletion the default fix.

EAS supports cache configuration and cache-key changes for invalidation.

---

# 57. Common failure: production secret in client bundle

### Symptom

A private credential appears in app configuration or compiled code.

### Response

Treat the credential as compromised:

```text
Revoke
 ↓
Rotate
 ↓
Remove
 ↓
Move privileged operation server-side
 ↓
Rebuild
 ↓
Verify
```

Do not simply rename the environment variable.

---

# 58. Build debugging decision tree

```text
Build failed
 │
 ├── Configuration error
 │ ↓
 │ inspect app config
 │
 ├── Dependency error
 │ ↓
 │ inspect Expo/native dependency versions
 │
 ├── Native build error
 │ ↓
 │ inspect Xcode/Gradle logs
 │
 ├── Signing error
 │ ↓
 │ inspect credentials + identifiers
 │
 └── Environment error
 ↓
 inspect EAS environment + variables
```

If the build succeeds but the app is wrong:

```text
Do not debug the build system first.

Inspect:
resolved configuration
+
artifact
+
runtime behavior
```

---

# 59. Definition of done

An Expo build is release-ready when:

```text
Correct source
 +
Correct configuration
 +
Correct environment
 +
Correct version
 +
Correct signing
 +
Successful build
 +
Artifact inspection
 +
Real-device testing
 +
Store validation
 ↓
 BUILD READY
```

The key rule is:

> **EAS Build creates the binary. Your release process proves that the binary is the right one.**
